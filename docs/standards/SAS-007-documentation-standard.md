---

# 1. Purpose

This standard defines the documentation requirements for every
artifact inside the SKOS ecosystem.

Documentation shall evolve together with the implementation.

---

# 2. Scope

Applies to:

- Engines
- Services
- Pipelines
- Connectors
- Runtime
- Kernel
- Schemas
- APIs
- Configuration
- Standards
- Repository

---

# 3. Documentation Principles

Documentation shall be:

- Accurate
- Complete
- Consistent
- Versioned
- Maintainable
- Discoverable
- Human-readable
- Machine-friendly where applicable

---

# 4. Mandatory Documentation

Every major component shall provide:

README.md

Specification

Architecture Notes

Configuration Guide

Usage Guide

Change History

---

# 5. README Structure

Every README should include:

- Overview
- Purpose
- Features
- Architecture
- Directory Structure
- Dependencies
- Installation
- Configuration
- Usage
- Examples
- Troubleshooting
- Related Documents
- License

---

# 6. Specification Document

Every component specification should define:

- Mission
- Responsibilities
- Inputs
- Outputs
- Dependencies
- Constraints
- Lifecycle
- Error Handling

---

# 7. Architecture Notes

Architecture documentation should explain:

- Component role
- Relationships
- Data flow
- Design decisions
- Extension points

---

# 8. API Documentation

Every public API should document:

- Endpoint or Method
- Parameters
- Return Values
- Error Codes
- Examples
- Version
- Compatibility

---

# 9. Examples

Documentation should include practical examples whenever useful.

Examples shall be executable or easily reproducible.

---

# 10. Diagrams

Architecture diagrams should be provided when they improve understanding.

Examples:

- Component Diagram
- Data Flow Diagram
- Lifecycle Diagram
- Dependency Diagram

---

# 11. Change History

Every maintained document shall include:

- Version
- Date
- Summary of Changes
- Related Build
- Related Operation

---

# 12. Language

Reference documentation shall be written in English.

Additional translations may be provided but shall reference the English version.

---

# 13. Cross References

Documents shall reference related standards, specifications and components.

Broken references shall be corrected before release.

---

# 14. Review Process

Documentation shall be reviewed whenever:

- Architecture changes
- Public interfaces change
- Major functionality changes

---

# 15. Compliance

Documentation is a mandatory deliverable.

A component is not considered complete until its required documentation has been completed and reviewed.

---

End of Standard
